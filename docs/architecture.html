System Design — v1

BookQuick: Real-Time Ticket-Drop Alerting

A production architecture for detecting the instant movie ticket booking opens for a tracked show, and fanning that alert out to every watcher in under a second — from a Manifest V3 browser extension down to the polling engine underneath.

Recommendation, up front

Build it as a queue-driven dynamic polling engine, not a scraper farm. The two problems that will actually break this system are (1) MV3 killing your extension's background context every 30 seconds, and (2) needing to notify thousands of watchers of one screening without a synchronous loop stalling the detector. Both are solved by the same move: decouple detection from delivery with a message broker, and let the extension be a thin, stateless client of a push channel instead of a thing that "runs" anything.

Start with plain HTTP polling against the booking site's own JSON endpoints (every major platform's web app calls one). Reserve headless-browser clusters and residential proxies for the specific targets that actively block that — don't build that complexity for platforms that don't need it.

Life of one alert

  1. Subscribe. User configures a watch in the extension popup (movie, cinema, format, date window, channel). This writes one row to watchers and, if new, a row to targets — extension never polls anything itself.
  2. Schedule. The scheduler ranks targets by proximity to expected release (see §3, dynamic interval) and drips job messages into the poll queue.
  3. Poll. A stateless poll worker pulls a job, makes one HTTP request (or headless-browser fetch for hardened targets), and writes the parsed status into a Redis key keyed by target ID.
  4. Diff. The worker compares the new status against the previous cached value. No change → done, job discarded in <50ms. Change from coming_soon → available → this is the trigger.
  5. Fan out. The worker does not loop over watchers itself. It publishes one TargetOpened event to the alert queue and returns immediately, keeping the detector hot for the next poll.
  6. Dispatch. A pool of notify workers consumes that event, pages through the watcher list for that target (batches of ~500), and pushes to each user's chosen channel in parallel. This is horizontally scalable independent of the poll workers.
  7. Deliver. Web Push hits the browser's push service (Chrome/Firefox relay this even if the extension's service worker is asleep — the OS wakes it). Telegram/WhatsApp/webhook calls go direct to those APIs. Every attempt is written to notification_log for auditability and retry.

Target end-to-end latency (status flip → notification received): under 1–2 seconds for Web Push and Telegram; webhook/WhatsApp add whatever the receiving system takes.

02

Tech Stack Evaluation

Three real candidates, evaluated on the axes that actually matter here: detection latency, how much day-to-day toil the on-call engineer eats, and what it costs at 100 tracked shows versus 10,000.

Option A — Node/TypeScript everywhere

Recommended BullMQ (Redis-backed queues) for both poll scheduling and alert fanout, Fastify for the API, Postgres for durable state, Redis doubling as cache + queue broker, Playwright for the hardened-target subset. Extension in TypeScript with a shared types package against the backend.

Option B — Python/Celery

Django or FastAPI, Celery + Redis/RabbitMQ for task scheduling, Postgres, Playwright (Python) for headless targets. Attractive if the team already leans Python for scraping/data work; Celery's periodic task + retry ergonomics are mature.

Option C — Go + Kafka

Go services for poll and notify workers, Kafka as the backbone (poll jobs and alert events as topics), Postgres, Chromedp for headless fetches. The right call only once you're firmly past 10k concurrent targets and Kafka's operational cost is justified by raw throughput and replay needs.

Trade-off matrix

DimensionA — Node + BullMQB — Python + CeleryC — Go + Kafka

Infra cost @ 10,000 targets ~$600–900/mo — Redis Cluster + more workers, still queue-broker-bound ~$600–900/mo, similar Best $/throughput at this scale — Kafka partitioning pays for itself
Operational risk Redis as broker is simple to reason about and monitor Celery + broker misconfig (visibility timeouts, lost tasks) is a classic footgun Kafka needs a dedicated owner; overkill risk for a team of 1–3

Verdict

Option A (Node/TypeScript + BullMQ + Postgres + Redis + Playwright) for build and first 12–18 months of scale. It minimizes the number of languages a small team maintains (extension, API, and workers all TypeScript — you can literally share the Target/Watcher types between backend and extension), BullMQ gives you delayed jobs, priority, rate limiting, and retries out of the box (exactly what dynamic polling needs), and Redis is one piece of infra that's both your cache and your broker. Re-evaluate Kafka only if a single target genuinely needs >10k watchers or you're tracking >10k shows concurrently — BullMQ/Redis will comfortably carry you well past your MVP and most production scale.

03

System Design & Schema Deep Dive

Database schema (Postgres)

-- One row per trackable release (a movie, broadly)
CREATE TABLE movies (
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  title         TEXT NOT NULL,
  release_date  DATE,
  external_ids  JSONB,               -- {"bms": "ET00312345", "district": "..."}
  created_at    TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE cinemas (
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  platform      TEXT NOT NULL,       -- 'bms' | 'district' | 'ticketmaster'
  name          TEXT NOT NULL,
  city          TEXT NOT NULL,
  external_id   TEXT NOT NULL,       -- platform's own venue ID
  UNIQUE (platform, external_id)
);

-- A specific (movie, cinema) pairing being polled — the actual "target"
CREATE TABLE targets (
  id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  movie_id         UUID REFERENCES movies(id),
  cinema_id        UUID REFERENCES cinemas(id),
  format           TEXT,             -- 'IMAX' | '2D' | '3D' | '4DX' | NULL = any
  date_window_start DATE,
  date_window_end   DATE,
  status           TEXT NOT NULL DEFAULT 'coming_soon', -- coming_soon | available | sold_out | closed
  poll_priority    SMALLINT NOT NULL DEFAULT 3,          -- 1 = hot (poll every few sec), 5 = cold (hourly)
  last_polled_at   TIMESTAMPTZ,
  last_changed_at  TIMESTAMPTZ,
  UNIQUE (movie_id, cinema_id, format, date_window_start)
);
CREATE INDEX ON targets (status, poll_priority);

CREATE TABLE users (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email        TEXT UNIQUE,
  created_at   TIMESTAMPTZ DEFAULT now()
);

-- One row per user-configured watch
CREATE TABLE watchers (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id      UUID REFERENCES users(id) ON DELETE CASCADE,
  target_id    UUID REFERENCES targets(id) ON DELETE CASCADE,
  channels     JSONB NOT NULL,        -- ["web_push", "telegram"]
  telegram_chat_id TEXT,
  webhook_url  TEXT,
  active       BOOLEAN NOT NULL DEFAULT true,
  created_at   TIMESTAMPTZ DEFAULT now(),
  UNIQUE (user_id, target_id)
);
CREATE INDEX ON watchers (target_id) WHERE active;

CREATE TABLE notification_log (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  watcher_id   UUID REFERENCES watchers(id),
  channel      TEXT NOT NULL,
  status       TEXT NOT NULL,         -- queued | sent | failed
  attempted_at TIMESTAMPTZ DEFAULT now(),
  error        TEXT
);
CREATE INDEX ON notification_log (watcher_id, attempted_at DESC);

Poll worker: scheduling, dedup, backoff

Dynamic interval, not fixed cron

Priority is a function of days-to-release: 7+ days out → poll every 30–60 min; 1–2 days out → every 2–5 min; inside the announced booking window → every 3–10 sec with jitter. Recompute poll_priority nightly from movies.release_date, and let the scheduler enqueue high-priority targets more frequently rather than running every target on one global cron tick.

Dedup via job idempotency key

Poll jobs use target_id + minute-bucket as a BullMQ job ID. If a job with that ID is already queued or in-flight, the enqueue is a silent no-op — this is what prevents duplicate requests when a target's priority changes mid-cycle or a worker retries.

Exponential backoff on failure

HTTP 429/503 or a timeout bumps that target's next-poll delay by base * 2^attempt (cap ~5 min), and increments a per-target fail_count. Three consecutive platform-level failures across different targets on the same platform trips a circuit breaker that pauses all polling for that platform for a cooldown window — this is what keeps one angry WAF from cascading into a ban of your whole IP pool.

Diff engine

Redis SETNX-style compare: GET status:{target_id}, compare to freshly parsed value, and only if different do you SET the new value and publish to the alert queue — a single Lua script (via EVAL) makes this atomic and sub-millisecond.

Rate limiting & proxy strategy

  • Prefer the platform's own JSON endpoints that their web/mobile app already calls (found via browser devtools network tab) over scraping rendered HTML — lighter weight, less likely to trip bot heuristics, and it's the same data a real user's browser requests.
  • Per-platform token bucket shared across all workers polling that platform (Redis-backed), e.g. cap at N requests/sec platform-wide regardless of how many targets you're tracking there — this is what "not getting IP-banned" actually comes down to.
  • Jitter every request (±20–30% of interval) so thousands of your polls don't land in synchronized bursts that look like a DDoS pattern.
  • Reserve headless-browser + residential proxy rotation for the specific platforms whose JSON endpoints are behind a WAF challenge (Cloudflare, PerimeterX, etc.) — this is meaningfully more expensive per-check, so gate it target-by-target, not globally.
  • Respect robots.txt and rate-limit headers (Retry-After) where present; back off on a 429 rather than rotating past it — treat rate limits as a real constraint, not an obstacle to route around.

Chrome Extension Architecture

Manifest V3 structure

manifest.json
├── background: { service_worker: "background.js", type: "module" }
├── content_scripts: [{ matches: ["*://in.bookmyshow.com/*", ...], js: ["content.js"] }]
├── action: { default_popup: "popup.html" }
├── permissions: ["storage", "notifications", "alarms"]
├── host_permissions: ["https://api.bookquick.app/*"]
└── options_page: "options.html"

content.js

Injected on booking-site pages. Reads the movie/cinema/showtime the user is currently viewing from the page DOM, and renders a "Watch for Booking" button overlay next to the native "Book Now" — this is the zero-friction entry point; the user never has to manually type a movie name.

popup.html + popup.js

The dashboard: lists active watches, lets the user add one manually (for cinemas without a content-script integration yet), pick format/date window, and choose channels. Reads/writes via the background service worker's messaging API — never talks to the backend directly.

background.js (service worker)

Deliberately kept thin. Its only jobs: relay messages between content script/popup and the backend API, register the Web Push subscription once, and handle chrome.notifications display when a push arrives. It does not poll anything or hold long-lived state — MV3 kills it after ~30s idle, so anything stateful lives in chrome.storage.local or the backend.

options.html

Account linking (magic-link email → JWT stored in chrome.storage.local) and default preferences (default channel, default format).

Solving the 30-second death: push, not polling

This is the core MV3 constraint the brief calls out, and the fix is architectural, not clever code: the extension never keeps a connection open waiting for alerts. Instead:

  1. On install/login, the service worker calls the Web Push API (PushManager.subscribe()) to get a browser-managed push subscription (endpoint + keys), and sends that subscription to the backend, stored on the watchers row or a separate push_subscriptions table.
  2. The backend's notify worker sends to that endpoint using the web-push library (VAPID-signed) when a target opens.
  3. Chrome/Firefox's own push service wakes the service worker even if it's been terminated — this is the entire point of Web Push: delivery is the browser vendor's problem, not yours. The worker's push event listener fires, and it calls chrome.notifications.create() to show the OS-level notification.

SSE or a raw WebSocket would require the service worker to hold a live connection, which MV3 will kill — those only make sense for a companion web-app tab that's actually open and focused, as a secondary channel. Web Push is the primary channel because it survives the worker being asleep.

05

Implementation Roadmap

Milestone 1 — MVP

Prove the core loop end-to-end for one platform, one region, manual target entry.

  • Postgres schema + Fastify API (auth, watchers CRUD)
  • Fixed-interval poll worker for a single platform's JSON endpoint, BullMQ + Redis
  • Diff engine + alert queue + one notify worker (Telegram only — fastest to stand up, no push-key infra needed)
  • No extension yet — targets added via a simple internal form

Milestone 2 — Robust Polling

Make the polling engine survive contact with real anti-bot defenses and scale past a handful of targets.

  • Dynamic priority scheduling by days-to-release
  • Per-platform token-bucket rate limiting + jitter
  • Exponential backoff + circuit breaker per platform
  • Playwright-based fallback poller for WAF-protected targets
  • Multi-platform support (BookMyShow, District, Ticketmaster adapters behind a common interface)

Milestone 3 — Extension UI

Zero-friction configuration, real push delivery.

  • Manifest V3 extension: content script overlay button + popup dashboard
  • Web Push subscription flow + VAPID keys on the backend
  • Magic-link auth, chrome.storage.local session
  • Web Push and Telegram both live as channel options

Milestone 4 — Scale & Edge Cases

Handle the 5,000-watchers-on-one-IMAX-screening case and the failure modes around it.

  • Batched fan-out in the notify worker (paginate watchers, parallelize with a concurrency cap, not one request at a time)
  • WhatsApp Business API + generic webhook channels
  • Notification log + retry/dead-letter queue for failed sends
  • Dedup guard: if a target flips available → sold_out → available again within minutes, don't double-alert the same watcher
  • Firefox port (WebExtensions API is largely MV3-compatible now)
  • Observability: queue depth, poll success rate, and alert latency dashboards — these are your early-warning signs of a platform tightening its bot defenses
06

Ethical & Legal Notes

Worth deciding deliberately before building, not after a cease-and-desist:

  • Prefer official or public endpoints over anything requiring credential theft, CAPTCHA-solving, or auth bypass — the endpoints this design targets are the same ones a logged-out browser already calls to render the page; that's a materially different posture than reverse-engineering an authenticated app API.
  • Check each platform's Terms of Service before adding it as a target. Some booking platforms explicitly prohibit automated access; others (many regional cinema chains) have no such clause. Where a platform offers a partner/affiliate API, use it instead of scraping — it's more stable for you too.
  • This system reads public availability status; it does not purchase, reserve, or hold seats. Keep it that way — an alerting tool is defensible in a way a bot that auto-checks-out tickets faster than a human is not, and mixing the two changes both the legal exposure and the fairness story.
  • Rate-limit yourself more conservatively than you technically have to. Being a good citizen of someone else's infrastructure is also just good survival strategy for the product's own uptime.
